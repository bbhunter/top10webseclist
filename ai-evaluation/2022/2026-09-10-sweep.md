### WebSpec — evidence digest

Read the [18-page January v1](https://arxiv.org/pdf/2201.01649v1.pdf), including
attack traces, performance discussion, related work, and compiler appendix.
Authors in this version are Lorenzo Veronese, Benjamin Farinier, Mauro Tempesta,
Marco Squarcina, and Matteo Maffei. The paper's 3 December 2021 submission to a
conference is not public publication. The [arXiv version record](https://arxiv.org/abs/2201.01649v1)
establishes 5 January 2022. Repository history could not be loaded, so no claim
is made about the exact first public commit; the targeted earlier-publication
search did not establish a pre-2022 release of the framework.

Contribution: model browser/API transitions in Coq, express ten security
invariants, compile a supported fragment to constrained Horn clauses for Z3,
and reconstruct minimal violating traces. The same model supports proofs of
fixes. The tested features include cookies, domain relaxation, CSP, CORS,
Trusted Types, blobs, service workers, and cache APIs. Configuration switches
let researchers compare older or proposed semantics. This is a reusable
offensive discovery method even though it also proves defenses.

The new host-prefix example sets `document.domain` in related-domain parent and
child, then writes a `__Host-` cookie through the parent's DOM: DOM authority
and the cookie setter's original-host attribution disagree. This requires the
victim to relax its domain; it is not an unrestricted host-cookie bypass.
The blob-policy example targets a proposed creator-versus-initiator inheritance
change. That discussion was already public in the earlier
[WHATWG issue](https://github.com/whatwg/html/issues/2593#issuecomment-885083373),
so it must not be separately claimed as a new 2022 primitive.

Closest prior is [Akhawe et al., 2010](https://theory.stanford.edu/~jcm/papers/browsermodel-csf-2010.pdf):
an executable Alloy web model already found concrete protocol/design attacks.
WebSpec therefore is not the first use of formal methods or automatic web
attack discovery. Its contribution combines a much broader modern browser
model with machine-checked proofs and bounded attack generation. The paper also
compares Featherweight Firefox, WebSpi and WIM. FuzzOrigin is a separate runtime
UXSS fuzzing method. **Do not credit the later browser-test verifier** described
by the current repository/2023 paper: January v1 outputs attack traces and
diagrams, not automatically executed browser test cases.

Skeptical search: `"WebSpec" "2021" browser security Coq`,
`"WebSpec" "2021" "SecPriv"`, `"WebSpec" "January" "2022" github`,
and `Akhawe Barth 2010 formal foundation web security pdf`. Checked the versioned
paper against later abstracts. Limitations: abstract model, finite bounds,
manually supplied invariants and optimization lemmas. Baseline solving can
take weeks; the paper reports large gains from lemmas/inlining/fixed arrays.
The framework was not run in this session.

Draft category reasons: original **75** for the modern-model/proof/discovery
combination over known model checking; transferability **76** across several
browser security boundaries; lasting **78** for reusable invariant/transition
reasoning; technical **82** for formal definitions, reconstructed traces and
proofs, bounded by model fidelity; practical **48** for specialist setup and
solver costs; clarity **78** for explicit traces, source link and appendix.

### Dangling iframes — evidence digest and reopened prior screen

Read the complete primary article and the complete
[2018 DOM-based dangling-markup predecessor](https://portswigger.net/research/evading-csp-with-dom-based-dangling-markup).
The 2022 timeline distinguishes private reports on 10 February from publication
on 14 June. The old evaluation grouped this with “Framing without iframes” as
narrow variants. New evidence warrants separate treatment: the 2018 source
explicitly requires one click with `base target`, or two clicks with the form
variant; the 2022 proof of concept extracts automatically after framing.

The attacker injects an unfinished iframe `name` attribute before a secret.
Markup until the matching quote becomes the nested frame's name. An outer
attacker page navigates that nested frame to `about:blank`, then reads the
retained name after the frame becomes accessible under the navigating origin.
This avoids both victim-side script execution and a resource URL containing
the captured markup. The supplied restrictive CSP example works without an
image exception. Constraints include HTML injection before the secret, a
frameable target, and applicable browser navigation/name behavior.

Closest prior: the 2018 article already combines dangling markup and retained
window names. Separately, a [February 2011 developer discussion](https://stackoverflow.com/questions/5092973/cross-domain-access-to-iframe-using-window-name)
already describes navigating to about:blank to access a cross-origin frame's
name. [Mozilla's 2021 bug 1685807](https://bugzilla.mozilla.org/show_bug.cgi?id=1685807)
also discusses retaining names during this navigation. These establish old
components, not the complete click-free injection/CSP exploitation recipe.
Originality is the useful combination and removal of interaction/network
requirements, not discovery of window.name or a universal SOP bypass.

Fresh skeptical searches included `"dangling" "about:blank" "2021"`,

`"about:blank" "window.name" "dangling" -site:twstalker.com -site:scribd.com`,
and `"window.name" "about:blank" CSP before:2022-06-14`.
The broader query exposed the 2011 precursor and the Mozilla issue; no earlier
complete same recipe was established. Search date filters are imperfect and
returned later pages, so dates were checked against the primary bodies.

Draft reasons: original **65** for a meaningful composition of old primitives;
transferability **68** across frameable HTML-injection targets; lasting **63**
for a useful browser-boundary lesson but quirk-sensitive payload; technical
**78** for the complete demonstrated chain with browser limits; practical
**80** for a short automatic PoC; clarity **88** for a clear progression and
explicit payload. No local browser reproduction was performed.

### XS-Leaks component model — evidence digest

Read the 15-page author-hosted paper through the appendices. The primary PDF
names the 2022 AsiaCCS conference and DOI 10.1145/3488932.3517416. The ACM page
could not be fetched. A search for a 2021 version did not establish one, but
**30 May is the conference start anchor, not a verified first-upload date**.

The paper extends XSinator's resource/inclusion/leak model with explicit
stateful components, split into attacker/victim contexts, browser, client OS,
server environment and web server. It separates transfer of private state into
a component from retrieval through an observable signal. The proposed search
process compares controlled resource variants and monitors component state
and execution, then manually determines a usable extraction technique.
It is a methodology, not a shipped automatic offensive scanner; Leakbuster
itself is a defense recommendation interface.

Section 5.1.1 supplies two concrete additional attack sketches. After a private
page loads n or n−1 subresources, send enough additional requests to reach a
server's per-connection keepalive count and detect whether a fresh connection
is needed. Alternatively, consume the remainder of an IP/endpoint rate-limit
budget and detect its error response. This uses server counters to infer
victim-dependent requests. Partitioned connections can stop the first route;
an IP-based rate limit remains shared independently of the browser's pool.
No measured end-to-end success rates or attack implementation are supplied.

Closest prior [XSinator, 2021](https://christianmainka.de/projects/casa/)
already formalized XS-Leaks, found 14 classes, and built a browser test tool.
Resource exhaustion, cache probing and browser connection-pool leaks are older
as well. The [connection-pool research wiki](https://xsleaks.dev/docs/attacks/timing-attacks/connection-pool/)
illustrates the latter, but its currently modified body is not a frozen 2020
artifact. The supported increment is the explicit cross-component state
method and server-counter adaptations; do not present all 38 classified leaks
as discoveries. Fresh queries used `"XS-Leaks" "rate limit" before:2022-05-30`,
`"XS-Leaks" "MaxKeepAliveRequests" before:2022-05-30`,
`"XS-Leaks" "rate-limiting" 2021`, `"xsleaks" "rate limit" github`,
and XSinator's 2021 formal-model title. They did not establish an earlier exact
server-counter attack, but were noisy. Main review should retain the distinction
between a defensible method and experimentally validated exploitation.

Draft reasons: original **63** for the component extension and server-counter
adaptations; transferability **72** across server/browser components; lasting
**73** for a reusable state-transfer/retrieval analysis; technical **64** for
formal reasoning with only attack sketches; practical **44** without a shipped
attack tool or calibrated measurements; clarity **72** for precise constraints,
worked examples and classification.

### Hand Sanitizers in the Wild — evidence digest

Read the complete [16-page author paper](https://swag.cispa.saarland/papers/klein2022hand.pdf),
including limitations, related work and appendix. Authors are David Klein,
Thomas Barber, Souphiane Bensalim, Ben Stock, and Martin Johns. The
[primary group news](https://www.tu-braunschweig.de/ias/news) explicitly dates
its public EuroS&P presentation to **8 June 2022**. The conference ran
6–10 June; the earliest public upload day remains unresolved. Data collection
in April/May 2021 does not establish publication in 2021. Exact title and
SemAttack searches did not establish an earlier public research release.

SemAttack turns rich dynamic taint-operation traces into sanitizer dependency
slices, models their JavaScript string and browser-encoding operations as
finite automata, intersects possible output with context-specific malicious
languages, and inverts the transformations to synthesize bypass inputs. It
then inserts those inputs into source URLs and validates them in a browser.
This addresses flows whose custom mutating sanitizer defeats ordinary fixed
payload generation. It is a discovery/tooling contribution, not a claim to
invent automata string analysis or XSS.

The implementation extends an existing automata library with JavaScript
semantics: first-only versus global replacement, encoding operations,
regular-expression shorthand, and relevant DOM serialization behavior.
Of 817 extracted sanitizers, 705 were modeled and 112 used unsupported
operations. Analysis flagged 88; ten could not be revisited, leaving 78.
Validation found **40 vulnerabilities, of which 36 were automated and four
required manual correction**. Thus the abstract's 51.3% validation figure
must not be restated as 40 fully automatic results. More significantly,
the modified browser had URL auto-encoding disabled to isolate application
sanitization, modeling environments such as legacy IE: these are not forty
proven exploits in an unmodified contemporary Firefox configuration.
Observed-path coverage, URL-only input, dependency approximation and automata
state growth further limit completeness and practical use.

Closest prior work: SemRep (2014), **Semantic Differential Repair for Input
Validation and Sanitization**, already performs automata-based reasoning
about validation/sanitization. The authors' [2015 primary overview](https://sites.cs.ucsb.edu/~bultan/publications/spin15.pdf)
corroborates that substrate. [Talking About My Generation](https://www.ias.cs.tu-bs.de/publications/talking_about_my_generation.pdf)
(EuroSec, 26 April 2021, DOI 10.1145/3447852.3458718) already uses dynamic
flow information for targeted DOM-XSS URL generation; the 2022 work explicitly
reuses it. The narrower increment is automatically extracting live client
sanitizer transformations, extending the semantic model to JavaScript/browser
operations, and reverse-solving their bypasses at scale. SANER, BEK and
Back in Black also predate this paper; related work explains their fixed
payload, manually translated, or server-side black-box settings.
The new method remains distinct from the listed 2022 prototype-pollution,
ODG and browser-origin-fuzzing work.

Fresh skeptical searches included exact title plus `site:publications.cispa.saarland`,
`"SemAttack" "2021"`, `"Semantic Differential Repair" 2014 Bultan`,
`"Talking About My Generation" 2021 XSS`, and exact title plus `2022 date`.
These establish substantial reused prior machinery, not an earlier equivalent
of the complete sanitizer-bypass pipeline. [Code](https://github.com/ias-tubs/hand_sanitizer)
and the [official artifact listing](https://ieeeeurosp.github.io/2022/artifacts/)
support reproducibility; execution was not attempted.

Draft independent scores: original **74** for the client sanitizer extraction
and reverse-solving increment over SemRep and the 2021 generator; transfer
**78** for custom client sanitizers across websites and operation classes;
lasting **76** for an enduring semantic-bypass testing method; technical **76**
for explicit modeling and validation, discounted for approximation and changed
browser assumptions; practical **65** for released tooling with supported-flow
and browser constraints; clarity **80** for detailed method, evaluation,
limitations and artifact. Weighted draft **75.2**.

### Hand Sanitizers / SemAttack — bounded prior-art correction (2026-09-10)

This follow-up supersedes the **75.2** draft above: the revised independent
score is **72.7**, still a survivor for the main reviewer. The original
assessment overstated the novelty of automatically extracting client-side
sanitizers and reverse-solving their bypasses. Those broad operations were
already established; credit belongs to the narrower DOM-XSS implementation
and integration described below. No new candidates, scorecards, curated lists,
or archive entries were changed in this follow-up.

**Full-source coverage and chronology.** Read Alkhalaf's complete dissertation
Chapter 2, “Modeling and Extraction of Sanitizer Functions,” printed pages
17–61 (PDF pages 36–80), plus relevant Chapter 4 passages on malicious-output
intersection and sanitizer pre-images. The [primary dissertation](https://sites.cs.ucsb.edu/~bultan/publications/AlkhalafDissertation.pdf)
is dated **June 2014** on its title and approval pages. Chapter 2 §2.5 cites
reference [3], the [full ICSE 2012 paper](https://sites.cs.ucsb.edu/~bultan/publications/icse12.pdf),
which was also read completely (11 pages). The dissertation's publication
record dates that conference to **2–9 June 2012**. Read the complete
[ViewPoints paper](https://sites.cs.ucsb.edu/~bultan/publications/issta12.pdf)
(11 pages), whose own first-page imprint dates ISSTA to **15–20 July 2012**.
These establish substantive public prior work comfortably before 2022;
no exact earliest upload date is inferred. Reread the complete
[2022 candidate](https://swag.cispa.saarland/papers/klein2022hand.pdf), including
its limitations and references. Local PDFs and complete page-marked text are
in `/tmp/hand-sanitizer-prior/`: `AlkhalafDissertation`, `icse12`, `issta12`,
and `hand2022`; `chapter2.txt` isolates the complete chapter. Code execution
and independent verification of the reported vulnerabilities were not done.

**What the earlier work already does.** ICSE 2012 §§III–IV runs valid and
invalid form inputs through HtmlUnit and an instrumented Rhino interpreter,
tracks input-dependent statements and concrete memory accesses, inlines
functions, and extracts validation slices. It models strings with DFAs,
handles branches and loops with approximation, identifies policy violations,
and tests generated counterexample inputs against the original function.
Thus neither JavaScript client-side extraction nor replaying generated
counterexamples is a 2022 invention. ViewPoints §§3–4 similarly extracts
client-side JavaScript slices, models them with automata, and compares their
accepted languages with server-side validation, confirming mismatches by
execution. Its framework configuration identifies form validation routines;
it does not find URL-to-DOM sanitizer boundaries as the candidate does.

The dissertation goes beyond pure Boolean validation: Chapter 2 includes
string-transforming sanitizers, an intermediate language, modeled native
operations, and unions of models from multiple representative executions.
Its Chapter 4, printed pages 125 and 144–145, explicitly intersects sanitizer
output with attack/policy languages and computes pre-images to identify
inputs producing bad outputs. This rules out credit for generic
“extract client code, model transformations, reverse-solve bad output.”
Chapter 2's client extractor operates around form submission/XHR; its dynamic
slices and reconstructed control structure are not identical to SemAttack's
observed operation traces.

**Remaining methodological delta.** Hand Sanitizers §3 selects mutating
sanitizer portions from rich URL-to-DOM taint flows using dangerous-character
operations and function-call boundaries. It normalizes those portions into
models that support first-only JavaScript replacement, URI/JSON operations,
and specific browser serialization behavior such as text-content to HTML.
It joins these models to the already published targeted DOM-XSS generator,
uses the surrounding injection context to define candidate output languages,
and puts the synthesized inputs into source URLs for browser validation.
This is a useful, nontrivial specialization and composition, supported by
large-scale extracted-sanitizer results, rather than a new extraction or
pre-image-analysis paradigm. Earlier replacement models and the specific
modern browser operation models are not interchangeable. Conversely, the
candidate does not establish a general precision improvement over the older
branch/loop analysis. Its observed paths, unsupported operations, numeric
approximations and single-witness fallbacks limit coverage.
