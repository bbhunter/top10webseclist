## Evidence digest A — OpenID Connect malicious endpoints

**Source boundary:** `/tmp/missed-2015/oidc.pdf` and `/tmp/missed-2015/oidc.txt`, original [v1](https://arxiv.org/pdf/1508.04324v1), read in full. Its actual title is *On the security of modern Single Sign-On Protocols – OpenID Connect 1.0*, with **five authors** (Vladislav Mladenov, Christian Mainka, Julian Krautwald, Florian Feldmann, Jörg Schwenk). The current arXiv abstract/title/authors describe v2 from January 7, 2016. Freeze the main attack at August 18, 2015. Later research says authors reported to the working group in October 2014; a private report is not itself public technical disclosure, and no dated public copy of that communication was established here.

**Core contribution:** a malicious provider-discovery document names honest registration and authorization endpoints but an attacker-controlled token endpoint. The client registers with the honest provider, the user authenticates to that same honest provider, and the client later sends the code and newly registered client credentials to the attacker. This crosses trust domains in server-side configuration before the visible login, while keeping the user's observed authentication genuine. The proof-of-concept uses MITREid Connect. The original paper explicitly says these optional extensions were not then used by publicly available systems, and excludes implicit flow from its demonstrated token-endpoint variant.

**Closest pre-cutoff comparisons:**

- [OpenID Connect Discovery draft 21](https://openid.net/specs/openid-connect-discovery-1_0-21.html), **December 19, 2013**, section 7.2 already warns that fake discovery documents can pair an impersonated issuer with attacker endpoints/keys. Its remedy is TLS and equality of requested issuer, metadata issuer and ID-token issuer. Candidate instead keeps the attacker's own issuer consistent and mixes honest registration/authorization with malicious token redemption; secrets escape before later ID-token verification could rescue the flow. This is a specific extension of a documented threat, not discovery of malicious metadata in general.
- [Cao et al., Protecting Web-based Single Sign-on Protocols against Relying Party Impersonation Attacks](https://iseclab.org/files/publications/Cao2014Protecting_Web.pdf), RAID **September 2014**, sections 2–3; fetched as `/tmp/missed-2015/cao2014.pdf` and `.txt`. Earlier work distinguishes forged RP identity from genuine initiation with a stolen redirect response, and diagnoses unauthenticated/one-way channels. Candidate's endpoints are learned during automatic server-to-server registration, rather than rewriting the browser's return URL or impersonating a known RP. The general channel-authentication problem is prior; the discovery/registration composition adds a concrete path.
- [Mainka/Mladenov/Schwenk malicious-IdP preprint](https://arxiv.org/abs/1412.1623v1), **December 4, 2014**, fully read during the preceding 2014 sweep (`/tmp/missed-2014/idp.txt`), and [Arnott association poisoning](https://blog.nerdbank.net/2009/03/08/openid-association-poisoning/), **March 8, 2009** (`/tmp/missed-2014/arnott.txt`): hostile providers, issuer/key binding and forged identities already existed. Neither verified source gives this honest-authentication plus dynamic-registration credential-redirection composition. A failed exact match is uncertainty, not proof of first invention.
- Existing 2012 traffic-guided SSO and 2014 SSOScan studies provide relevant testing background; they do not make every later server-side configuration attack a duplicate. The author paper's assertion that previous tools cannot find this is a claim, not independently benchmarked here.

**Same-year companion:** the [October 5, 2015 author post](https://web-in-security.blogspot.com/2015/10/attacking-openid-connect-10-malicious.html), read in full, adds attacker `userinfo_endpoint` receiving the bearer access token, including implicit flow. If retained, group this artifact with the August work and assign the user-info contribution its own October cutoff. Do not use it to upgrade the August paper's tested coverage. The draft score below evaluates the August disclosure only.

## Evidence digest B — Netty cookie parsing / HttpOnly exfiltration

**Full source:** preserved May 15 article at [`archived-references/md/2015/linkedin-linkedin-security-practices-find-out-how-we-protect-you.md`](../../archived-references/md/2015/linkedin-linkedin-security-practices-find-out-how-we-protect-you.md), lines 487–585 at inspection. Read entire article including parser fragment, outputs, Play exploitation and credits. Current original `https://security.linkedin.com/blog-archive` returns 404, so use this intact archived primary body rather than `/tmp/missed-2015/linkedin.txt` (that temporary file is only the failed fetch).

**Date and exclusion:** [Netty PR 3748](https://github.com/netty/netty/pull/3748), **May 6, 2015**, explicitly links permissive parsing to HttpOnly escaping; [Play advisory](https://www.playframework.com/security/vulnerability/CVE-2015-2156-HttpOnlyBypass), **May 9, 2015**, identifies response reflection of cookie values as the prerequisite. The detailed article is **May 15**. Therefore use May 6–15 for contribution-level cutoff uncertainty, not April 8 private reporting. URL helper drops `blog-archive#05152015` because `blog-archive#11232015` is nominated. This does **not** establish that the May research was nominated: the curated title and November fragment point to “Who Are You? A Statistical Approach to Protecting LinkedIn Logins (CSS UI Redressing Issue).” Main reviewer should preserve separate article identity even though the archive captures both on one page.

**Core contribution:** an unclosed initial single/double quote causes Netty to consume subsequent cookie name/value pairs as part of the first cookie. If that first cookie is the reflected CSRF-token cookie, the otherwise HttpOnly session cookie becomes application response content accessible to injected same-origin script. The new capability is turning a selective, otherwise reasonable cookie reflection into reflection of a different protected cookie through disagreement over field boundaries.

**Prior comparisons:**

- [Mozilla MFSA 2009-05](https://www.mozilla.org/en-US/security/advisories/mfsa2009-05/), **February 3, 2009**, and its [original bug](https://bugzilla.mozilla.org/show_bug.cgi?id=380418): JavaScript reads Set-Cookie via XHR. This requires browser API exposure of response headers; it does not use server-side cookie-value swallowing.
- [UI redressing mayhem / HttpOnly bypass](https://web.archive.org/web/20170903113359/http://blog.nibblesec.org/2012/12/ui-redressing-mayhem-httponly-bypass_19.html), **December 2012**, preserved under `archived-references/md/2012/blog-nibblesec-org-ui-redressing-mayhem-httponly-bypass-paypwn-style.md`, discusses Apache CVE-2012-0053: oversized/malformed Cookie header reflected by an error response. This already demonstrates malformed-cookie-to-body HttpOnly exfiltration. Netty supplies a distinct reflection path: no error page/full-header reflection required, only a normally reflected individual cookie whose parser value expands across boundaries.
- [RFC 6265](https://www.rfc-editor.org/rfc/rfc6265.html), **April 2011**, gives excluded octets and quoted syntax. A grammar describes the building block and expected behavior, not automatically the later exploit. Earlier cookie-path/cookie-injection references in 2006/2008 cover setting/ordering cookies but did not establish this value-swallowing reflection capability.

**Corrections and limits:** article says “universal” and “default” in places, but the contemporaneous Play advisory narrows the condition to apps that reflect cookie values, e.g. nondefault cookie-based CSRF storage. Score the narrower evidenced attack. Same-origin XSS or another cookie-setting route plus readable response is needed; cookie order and reflection must be arranged. Do not claim all Netty applications exfiltrate cookies. No live target or historical PoC was executed.

### Full-source digest

The article describes a legitimate service worker that looks up requests in its
cache, otherwise fetches and stores their responses. Its novel chain begins with
an **open redirect**, not an existing XSS: a CORS-mode request through the
redirect retrieves attacker-controlled content whose server permits CORS. The
worker stores that final response against the original request. A later visit
to the cached URL obtains the foreign content under the victim URL rather than
following the original redirect. The source explicitly requires both
`Access-Control-Allow-Origin: *` at the attacker endpoint and a CORS-enabled
request to populate the cache. It proposes checking response/request URLs.

**Reviewer reconstruction of the reusable idea:** permission to read a response
across origins is not permission to execute it as a document in the requesting
origin. A programmable cache can join a request name, response body, origin and
later rendering context in ways a normal redirect would not. The attack exploits
that mismatch across *two uses* of the cached entry. Cache persistence is a
consequence; the new capability is reaching same-origin execution without the
initial script-execution or network-interception prerequisite of the closest
persistence attacks.

Preconditions materially narrow the result: the victim must have a relevant
active service worker, its caching logic must accept and reuse the redirected
response, the attacker needs a usable open redirect and CORS-enabled population
path, and the subsequent navigation must select the poisoned entry. An arbitrary
open redirect alone is insufficient. The article uses sample applications and
predicts future vulnerable deployments; it does not establish that almost all
service workers are vulnerable. That prediction and the title's "forever"
wording are not measured findings. Cache deletion, eviction and application
updates can bound persistence.

The May 25 source supplies a complete inline Cache API overwrite example for
the **already-known** first component, but explains the redirect chain mainly
in prose and links to mutable sample worker code. The main method is explicit
enough to evaluate, while exact version reproduction is weaker than a pinned,
self-contained redirect demo. No live demo was run against external sites or
present-day browsers. The May 27 clarification says poisoning must occur with a
CORS response before an opaque response is cached; that is useful version
context, but is excluded as an extra May 25 reproducibility benefit.

   discusses the consequences and scope. Both were read in full. This already

   network. It does not supply the no-MITM redirect/CORS chain.

3. **Service-worker response-origin confusion was already understood generally.**
   The [30 April–1 May 2015 Chromium net-dev discussion](https://groups.google.com/a/chromium.org/g/net-dev/c/ISwnbx4vozw/m/lAYChmvAZtIJ)
   explicitly warns about treating intercepted responses as coming from the

   request/response processing layers. Its full visible thread was read.
   This is important prior understanding, so the candidate is an extension,
   not the first discovery of origin confusion involving service workers.
   The visible thread does not show a victim application's open redirect plus
   CORS cache-fill followed by document replay. Its linked internal-issue/design

   earlier public examples.

4. **Earlier cache-origin warnings describe a different capability.**
   The [18 March 2014 SRI draft, §§4.1.1–4.1.2](https://www.w3.org/TR/2014/WD-SRI-20140318/#origin-confusion)

   script-tag injection and a digest-keyed cache. This reduces any broad claim
   that cache identity confusion is new, but does not supply the candidate's
   programmable-cache redirect chain or its prerequisites.
