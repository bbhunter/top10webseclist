## Survivor 1 — The Remote on the Local

**Date/source.** The [original SecWeb programme](https://secweb.work/2020.html) lists the paper for **11 September 2020, 16:00–16:20 CEST**, with four authors including Somé; it says the programme was released 5 August. The linked 11-page source explicitly calls itself a SecWeb 2020 work-in-progress. September 11 is a verified substantive public disclosure bound; August 5 programme release alone does not prove the full PDF was public that day. The [2021 project](https://swcacheattack.secpriv.wien/) and revised three-author WOOT paper must not silently replace this source. Full extracted source read: `/tmp/missed-2020/remote.pdf`, `remote.txt`, 54,707 characters.

**Contribution and evidence.** Section 3 treats a script already running in a page as weaker than the browser’s origin-wide Cache API state it can overwrite. By changing a cached Response and letting a benign service worker serve it on reload, an attacker strips CSP/X-Frame-Options/Referrer-Policy/Feature-Policy headers, or changes the order of security bootstrapping scripts and removes `Object.freeze`/`const` protections. The page then starts without policy or runs attacker code before protected objects are established. Same-origin/CORS-readable response bodies can be edited; opaque response restrictions still matter. Permission-policy stripping does not grant hardware access: the user still must consent. Existing worker deployment/caching and initial script execution are preconditions; it is not XSS from an arbitrary unaffiliated page.

The full source gives concrete cached policy examples from Twitter, Pinterest, The Hacker News and ComputerBase, step-by-step header stripping and reload behavior, plus an instrumented Chrome/Puppeteer/Mitmproxy crawl of 110,000 sites. Figure 4 reports 6,197 sites with workers and 3,145 using Cache API. Figure 7 gives 375 sites with cached CSP, 744 XFO, 296 referrer policy and 20 feature policy. Those are cached-policy observations conditional on obtaining initial script execution, not verified live XSS counts. Runtime hooks trace API calls across selected pages; authenticated collection is discussed but not a fully distinct quantified result. The proposed isolated worker cache is defensive follow-on value.

**Closest earlier evidence.** Vela’s [25 May 2015 full article](https://sirdarckcat.blogspot.com/2015/05/service-workers-new-apis-new-vulns-fun.html), `/tmp/missed-2020/sirdarckcat2015.txt`, already shows same-origin page code replacing a worker cache Response with attacker HTML and explains persistent XSS. Its example sets response headers as well. Thus origin-shared Cache API poisoning and persistence are prior art, not original 2020 primitives. The 2020 delta is a systematic interpretation as a policy/initial-execution boundary bypass plus measurement of these specific opportunities. Earlier [Braun 25 March 2017](https://frederikbraun.de/sw-sri-challenge.html), local `braun2017.txt`, bypasses worker-based SRI enforcement using srcdoc/sandbox/registration/RPO routes, rather than mutating a benign worker’s cache; the distinction is useful but not proof of a new class. The 2018 PWA offline-cache history oracle measures state rather than writes policy. Jan 2020 Akamai assumes malicious worker registration, which is stronger than the cache-only corruption here.

## Survivor 2 — Security Study of Service Worker Cross-Site Scripting

**Date/source.** [ACSAC programme](https://www.acsac.org/2020/program/final/s297.html), author [bibliography](https://success.cse.tamu.edu/publication_bib/) and paper identify **7–11 December 2020**, DOI `10.1145/3427228.3427290`; no earlier substantive public copy verified. The author-host URL’s `/2020/07/` path is not proof of July publication. Authors: Phakpoom Chinprutthiwong, Raj Vardhan, Guangliang Yang, Guofei Gu. Full 12-page extracted paper read at `/tmp/missed-2020/swxss.{pdf,txt}`, 72,846 characters.

**Mechanism.** Document URL parameters are passed to `register('/sw.js' + location.search)`, then read via worker `self.location` and incorporated into `importScripts`, or decoded into `Function`. The registered entry script is valid and same-origin, but the data reaches cross-origin executable imports inside the worker. Attackers can capture fetch event handling during initialization and alter later page responses. A weak attacker needs only a crafted link/frame where the application forwards parameters; stronger cases require preexisting page script execution to make the registration call. This differs from uploading the malicious worker itself or poisoning page HTML in its cache.

**Methodology/results.** SW-Scanner instruments code with Babel/Iroh, tracks worker URL values into `importScripts`, Function/eval and timer sinks, hooks operations and imported local copies, and uses a baseline execution to preserve branches when boxed taint values could change types. The December 2019 Tranco corpus yields 7,060 worker sites, 6,182 successfully parsed, 2,525 parameterized; 40 confirmed vulnerable sites include 11 weak-attacker sites. The paper filters 80 URL/import reports down to 35 whose taint can change the imported origin, plus four encoded/hash URLs and one direct Function case. Manual DevTools confirmation checks controlled imports before event setup; 100 nonreported sites receive extra path analysis. Tool and data release are stated. It is a purpose-built exploitation-oriented taint workflow, not merely a census of ordinary XSS.

**Precise earlier comparisons.** [Larsen 17 June 2016](https://c0nradsc0rner.com/2016/06/17/xss-persistence-using-jsonp-and-serviceworkers/) is explicitly cited: same-origin JSONP can manufacture the registered worker body. Its original host failed DNS in this run, so the detailed prior-art characterization is limited to the candidate’s own related-work description plus the independently read Chromium 2017 security FAQ from the 2018 sweep. Vela 2015 writes the page-response cache, not injected configuration inside a benign worker. Akamai January 2020 uploads a malicious same-origin worker, whereas this candidate requires neither upload nor malicious entry-script bytes in the weak-attacker case. General DOM taint tracking is old (FLAX, 25 Million Flows, DOMsday), so credit the context transition, source/sink modeling and confirmed workflow rather than first taint analysis. Fresh pre-December searches did not establish an earlier identical query-parameter-to-import worker exploit; that negative result alone is not a first-ever claim.

**Material correction using pre-cutoff evidence.** Section 4.2 says imported files are not checked for freshness unless the main worker changes, and Section 6.3 extrapolates approximately 40 days of attacker persistence from archived main-file update intervals. [Chrome’s 19 September 2019 primary explanation](https://developer.chrome.com/blog/fresher-sw/), `/tmp/missed-2020/fresher2019.txt`, already says Chrome 78 checks imported scripts, matching Firefox 56 and Safari. Thus that broad argument was stale at publication. A malicious imported URL can remain malicious after a refetch, but absence of main-file changes alone does not establish a 40-day infection guarantee. Preserve the confirmed injection mechanism; do not copy the claimed persistence duration. The paper also overstates some event-listener exclusivity language; no independent historical execution was performed here.

## Survivor 3 — Information Leaks via Safari’s Intelligent Tracking Prevention

**Date/source.** [arXiv v1](https://arxiv.org/abs/2001.07421) submitted **21 January 2020 10:09:17 UTC**, six pages; [Google research record](https://research.google/pubs/information-leaks-via-safaris-intelligent-tracking-prevention/) confirms authors Artur Janc, Krzysztof Kotowicz, Lukas Weichselbaum, Roberto Clapis. Full v1 read at `/tmp/missed-2020/itp.{pdf,txt}`, 19,331 characters. The private WebKit report is access-restricted; its earlier submission is not public disclosure evidence.

**Important earlier partial disclosure.** WebKit’s [10 December 2019 post](https://webkit.org/blog/9661/preventing-tracking-prevention-tracking/), `/tmp/missed-2020/webkit2019.txt`, already explains user-specific anti-tracking classification as a tracking vector, differential referrer/cookie treatment, and mitigations; it credits Google. Accordingly, 2020 cannot claim discovery of the general anti-tracking-state leak. The January report adds concrete residual-strike measurement, artificial pinning behavior and cross-site search construction; those are the specific 2020 extension evaluated here. It openly says some issues were already fixed in December, reducing immediate testing availability at its publication.

**Technical digest.** The on-device prevalent-domain set is eTLD+1-scoped and appended as distinct sites load a domain cross-site. Testing found three distinct loading domains sufficient. The report describes reading classification through long-referrer request failure versus truncation success, credential-dependent loads and observable redirects. Controlled additional loading origins push a target over the threshold: the number of added strikes reveals prior cross-site usage, exposing visits to sites with unique media domains. Encoding bits through selected artificially classified domains yields a global identifier; short-lived documents avoid adding probe strikes and saturating the bits. Preloading two strikes for a media domain then framing a private search query makes the third strike contingent on a result’s media inclusion, furnishing a cross-site search oracle. Forcing classification can also suppress authenticated resources and disrupt multi-origin applications. It requires readable side effects, chosen domains/context control and application behavior; not universal inbox exfiltration. Code/PoC URLs exist for four attacks, and the long-referrer mechanism was reportedly tested on 100+ domains, but not every enumerated variant has equivalent empirical validation.

**Prior art/recheck.** [WHATWG Fetch issue 903](https://github.com/whatwg/fetch/issues/903), **8 May 2019**, already describes attacker-controlled overlong Referer as a cache/error/cookie-size side channel and proposes a cap. API issue body/comments saved as `referrer2019.txt` and `referrer-comments.txt`; thus the long-header oracle alone is not new. The report explicitly says ITP bit pinning is analogous to HSTS pinning (2015), and cites established 2015 cross-site search. The contribution is composing a trainable shared privacy classifier with readout to expose hidden cross-origin actions, particularly residual-strike and search-result tests. The December 2019 WebKit post is the closest ITP disclosure, but does not provide those recipes. Fresh searches for pre-January ITP strikes/pinning/search found no earlier detailed equivalent; confidence remains moderate because the private report and precise timing of all public PoC uploads could not be verified. Later fixes or citations did not raise the value score.
