## Survivor 1: Well, That Escalated Quickly!

**Michael Cherny and Sagie Dulce; July 2017.** [Original 18-page whitepaper](https://blackhat.com/docs/us-17/thursday/us-17-Cherny-Well-That-Escalated-Quickly-How-Abusing-The-Docker-API-Led-To-Remote-Code-Execution-Same-Origin-Bypass-And-Persistence_wp.pdf), [Black Hat program](https://blackhat.com/us-17/briefings.html). Full title: *How Abusing Docker API Led to Remote Code Execution, Same Origin Bypass and Persistence in the Hypervisor via Shadow Containers*. Traced directly from `archived-references/md/2016-17/blackhat-com-black-hat-usa-2017.md`, around line 1960; absent from curated entries and earlier evaluation candidates.

**Date/source:** cover states July 2017 and the original conference program corroborates the year. Exact first technical release day remains unresolved within July. Complete extracted whitepaper text was read, all 18 pages through the conclusion. Image-only code/figures were not independently transcribed or executed; the textual attack sequence is explicit. Direct PDF download returned HTTP 403; the web PDF reader worked. The author's companion blog failed retrieval.

**Evidence digest:** A browser-compatible Docker build POST supplies an initial unprivileged container. Using host networking, that foothold answers LLMNR requests first with its own address, then loopback after browser cache expiry. The browser consequently gains same-origin access to the local Docker API without changing external DNS. The paper also describes persistence by transferring state between a restart-enabled container and the VM during shutdown/startup. Its invisibility claims exceed the demonstrated testing; this review credits the concrete chain, not universal evasion.

**Closest pre-cutoff comparison:** [Jackson et al., Protecting Browsers from DNS Rebinding Attacks, CCS 2007](https://crypto.stanford.edu/dns/dns-rebinding.pdf), especially §§3–5, already demonstrates rebinding for intranet/loopback access and proposes filtering external DNS answers. [BreakPoint Labs' 31 October 2016 primary practitioner demonstration](https://breakpoint-labs.com/multicast-name-poisoning/) establishes LLMNR/NBNS spoofing for credential interception; it does not describe this browser-origin transition. Docker's own older TCP/CSRF warning is quoted and attributed on page 5 of the candidate: exposed Docker APIs are not credited as a newly discovered general risk. The extension is the remotely bootstrapped virtual-network name-resolution route into the full API, crossing the restrictions of the first simple request.

Fresh skeptical searches used NetBIOS/SOP, LLMNR/browser and pre-July Docker build/CSRF terms. They also found [webpack-dev-server issue 887](https://github.com/webpack/webpack-dev-server/issues/887), publicly posted in April 2017: ordinary DNS rebinding reaches a developer service and its backend proxy, whereas the candidate gets a local responder foothold and changes non-DNS resolution. No exact prior chain was established. Absence of an exact search result is not proof of first invention.

**Draft verdict:** meaningful combination/adaptation. **Confidence:** Medium. Score only the publication-time evidence:

## Survivor 2: Fingerprinting Firefox users with cached intermediate CA certificates (#fiprinca)

**Alexander Klink.** [Full original article, 21 February 2017](https://shiftordie.de/blog/2017/02/21/fingerprinting-firefox-users-with-cached-intermediate-ca-certificates-fiprinca/); [original Mozilla report 1334485](https://bugzilla.mozilla.org/show_bug.cgi?id=1334485). Discovered by following the author's adjacent research from SMTP-over-XXE, itself found in the protocol-injection search. The full article was read and saved at `/tmp/websec-sweep-2017/fiprinca.html` (13,808 bytes). No PoC was executed.

**Cutoff:** the author reports private submission on 27 January 2017; the report became public by the 21 February article. Exact public-opening time was not recovered, so use the **27 January–21 February 2017 interval**, treating intervening material as uncertain rather than earlier. Year confidence high.

**Evidence digest:** Incomplete TLS chains make image loading depend on Firefox's cached intermediate certificates. Load/error events expose those bits remotely, including normal-profile state available in private browsing. The author builds a probe corpus for 300-plus intermediates from Internet-wide TLS scans. Naturally visited sites can change bits, and independently operated probe servers can change configuration. Unique identification accuracy, location/interest inference and deliberately planted persistent identifiers are proposed possibilities, not measured guarantees.

**Precise contribution versus primary prior art:** [Aggarwal, Bursztein, Jackson and Boneh, An Analysis of Private Browsing Modes in Modern Browsers, USENIX Security 2010](https://www.usenix.org/events/sec10/tech/full_papers/Aggarwal.pdf), §5.2, explicitly says cached CA chains reveal visits such as government sites to a **local** attacker. This is preserved in the 2010 private-browsing Markdown around line 624. Its client-certificate session linkage is also separate from intermediate-CA state. Klink adds the **remote third-party probe** through certificate-chain completion and a corpus-building method, rather than first recognizing that certificate caches reveal history. Existing 2017 hardware fingerprinting and FP-STALKER do not represent this TLS-cache oracle.

Fresh prior-art path searched certificate-cache privacy, TLS session tracking and HSTS supercookies. Those confirm older security-state tracking concepts; generic cookie replacement and private-mode linkage are not themselves the novel contribution. The primary 2010 source, reopened after the article, is the closest verified cache-specific predecessor. Updated WebKit tracking documentation and later reports were not treated as dated pre-cutoff proof. No exact earlier remote incomplete-chain oracle was established; confidence remains Medium.
