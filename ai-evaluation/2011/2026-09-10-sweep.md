### Evidence digest and interpretive limits

**Problem/method/result:** the report compares framework sanitizer guarantees
with application needs. It combines browser context/transition definitions,
framework capability tables, ten Django template inspections, and dynamically
sampled PHP output-context inference across eight applications. Its policy
function represents sanitizer selection by context plus application attributes,
including roles and filter choices. The reusable contribution is a structured
audit of the gap between a framework's automatic escaping and an application's
actual data lifecycle, rather than discovery of context-sensitive escaping.

Read locations in the February report: §§2.1–2.5 for context-chain safety and
browser transformations; Tables 2–3 for DOM access behavior; §3/Table 4–6 for
framework capabilities and Django observations; §4.1 for instrumentation;
§§4.3–4.4 for context coverage and policy selection; §6 for acknowledged prior
models. The ESORICS version gives the same core argument in §§2–4 and its
appendix, and refers readers back to the report for detailed methodology.

**Reviewer analysis:** a useful testing procedure follows from this combination:
identify where untrusted values enter templates, compare each insertion's parser
context with its chosen encoder, follow subsequent DOM reads and reparsing, then
check whether equal syntactic contexts intentionally require different policies.
That last check prevents an audit from treating every omitted or differing
sanitizer as a bug: privilege and allowed markup can change what the correct
operation should be. It also exposes the opposite problem, where a framework's
single policy per context cannot express the application's requirement.

The source is a methodology study, not a complete exploit scanner or a proof
that studied applications are secure. Its PHP analysis forks execution to probe
string-taking functions with an attack string, heuristically recognizes
sanitizers using edited outputs, marks data, and classifies emitted output with
a modified Python HTML5 parser. This is **not an instrumented-browser
evaluation**, complete path exploration, or proof of sanitizer correctness.
Manual interactions supplement fuzzing; authentication/state/path coverage and
heuristic classification remain material limits. The method can therefore
demonstrate observed requirements without proving that unobserved contexts do
not occur. A full reproduction would require rebuilding the instrumentation and
recovering the original application versions and interactions.

Corrections and cautions retained after rechecking the original:

- Its prose repeatedly says **13 frameworks**, but Table 4 visibly names
  **14 rows** (including the three Perl and five PHP entries). The later
  proceedings says 14. Do not describe that as a newly added fourteenth
  framework without a version comparison; the inconsistency is already present
  in February. Count-sensitive claims are not the basis of the novelty score.
- The Django table measures context placement and escaping choices, **not
  confirmed XSS prevalence**. The original explicitly reports manual
  sanitization on further inspection. Neither a non-HTML sink nor the presence
  of a mismatched default alone establishes attacker control and exploitability.
- Treat the phpBB `getAttribute` → `innerHTML` example as evidence of a
  transformation/reparse hazard. Its abbreviated literal-script explanation
  was not independently reproduced on a period browser; no confirmed exploit
  count is inferred from that paragraph. The numeric entity example also omits
  the `#` in the printed escape. Those presentation defects constrain how
  literally its schematic payloads should be reused.
- The original's claim that observed whitelisting avoids browser variance is
  an empirical observation/inference, not a proof covering all browser inputs.
  It does not overturn BLUEPRINT's earlier parser-difference threat model.
