# Research Evaluation

## Candidate

- **Title:** Heartbleed (2014 rank 1)
- **Author or organisation:** Neel Mehta (Google), and independently Codenomicon; original vendor advisory credits Mehta.
- **Publication date:** 2014-04-07
- **Reference:** [Nominated reference](https://web.archive.org/web/20160403035045/http://heartbleed.com/); [local archive](../../archived-references/md/2014/heartbleed-com-heartbleed-bug.md).

## Core Contribution

An attacker-controlled heartbeat length makes a cryptographic endpoint return process memory beyond the supplied payload. The reusable lesson is to compare nested message lengths with actual buffer bounds at both client and server endpoints. The original vendor disclosure supports a remote disclosure of up to 64 KiB; it does not establish that every response contains a useful secret.

## Prior Art

- **Novelty cutoff:** 2014-04-07. Evidence and version limits below.
- **Earliest credible pre-cutoff related work:** [OpenSSL advisory, 4 January 2012](https://openssl-library.org/news/secadv/20120104.txt), CVE-2011-4576: uninitialised SSL 3.0 padding could reveal previously used memory to a peer. This is actual memory-disclosure prior art, with different triggering and size constraints.
- **Closest pre-cutoff equivalent work:** The same 2012 disclosure is the closest verified outcome-level comparison, not an equivalent heartbeat exploit. [RFC 6520, February 2012](https://www.rfc-editor.org/info/rfc6520/) specifies heartbeat framing and bounds validation; it establishes background requirements, not prior publication of this exploit.
- **Evidence boundary:** Read the complete archived Heartbleed site, but it contains later April updates. Score the core established by the [7 April vendor advisory](https://openssl-library.org/news/secadv/20140407.txt), using the site only where consistent with that disclosure. Later key-recovery demonstrations, remediation experience, prevalence, and claims about universal retrospective decryption are excluded.
- **Candidate's distinct contribution as of the cutoff:** A distinct, attacker-selected heartbeat over-read and much more useful disclosure surface than leaking padding bytes. The marginal research contribution is still an instance of an established memory-disclosure/bounds-validation problem; this is not a claim that Heartbleed was already published.

## Scorecard

| Category | Score | Weight | Weighted score | Reason |
|---|---:|---:|---:|---|
| Original contribution | 40/100 | 25% | 10.00/25 | Real new disclosure route, but the central bounds-validation and returned-memory failure is incremental against actual earlier OpenSSL leakage. |
| Transferability | 55/100 | 20% | 11.00/20 | Tests of nested lengths generalise across protocol parsers; the specific capability depends on this heartbeat implementation. |
| Lasting value | 55/100 | 20% | 11.00/20 | Useful malformed-length test case and endpoint audit lesson; limited additional methodology beyond established memory-disclosure testing. |
| Technical soundness | 85/100 | 15% | 12.75/15 | Vendor identifies the defective check, direction of disclosure, affected releases, and upper bound; broader secret-recovery claims are not assumed. |
| Practical usability | 80/100 | 10% | 8.00/10 | Concrete, remotely reachable malformed-message condition makes useful testing straightforward under the stated prerequisites. |
| Clarity and reproducibility | 70/100 | 10% | 7.00/10 | The original advisory pinpoints the extension and bounds failure; it provides less reproduction detail than a full experimental paper. |

**Final score: 59.8/100** (moderate)

## Reverification

- **Candidate facts rechecked against:** Reopened the original vendor advisory and the archived site, and compared the January 2012 advisory with RFC 6520.
- **Cutoff audit:** Dates and original-version exclusions are recorded above. Publication-time evidence is used for all six categories; potential is the evaluator's forecast, not observed later influence.
- **Independent prior-art check:** Local pre-2014 searches for memory disclosure, heartbeat, over-read, and padding were followed by a separate OpenSSL advisory-history search. That found a genuine earlier disclosure, while a 2011 status-request over-read was a crash report and was not treated as an exfiltration equivalent.
- **Strongest challenge to the result:** A repeated remote read of substantially more process memory is a useful new primitive, not merely publicity surrounding an ordinary crash. That deserves originality credit even though memory disclosure itself was known.
- **Benefit-of-doubt check:** The strongest plausible reuse is a test family for inconsistent nested lengths in cryptographic clients and servers. Neither a quick patch nor later fame settles that potential.
- **Changes after reverification:** Retained moderate marginal-contribution scores after distinguishing the heartbeat route from the earlier padding leak. Excluded later demonstrations and did not use the RFC alone to claim an exploit predecessor.

## Verdict

**Useful application or case study**

- **Archive decision:** Include as a supporting reference
- **Confidence:** Medium
- **Reasoning:** This exposes a consequential new instance of a known failure pattern. The supporting-reference recommendation reflects marginal research value under this rubric, not operational importance.
- **Evidence gaps:** The precise day-one version of every Heartbleed-site paragraph was not recovered. Secret-extraction breadth and day-one reproduction completeness are therefore not inferred from the updated site.

# Research Evaluation

## Candidate

- **Title:** ShellShock (2014 rank 2)
- **Author or organisation:** Stéphane Chazelas; coordinated technical disclosure by Florian Weimer / Red Hat.
- **Publication date:** 2014-09-24
- **Reference:** [Nominated reference](https://web.archive.org/web/20160403035045/https://cve.mitre.org/cgi-bin/cvename.cgi?name=CVE-2014-6271); [local archive](../../archived-references/md/2014/cve-mitre-org-cve-cve-2014-6271.md).

## Core Contribution

A shell imports functions from environment-variable values and executes commands trailing a function definition during startup. Consequently, ordinary request metadata can become code without the application deliberately placing that value in a shell command. The insight is to audit implicit interpretation during process creation, including indirectly invoked shells.

## Prior Art

- **Novelty cutoff:** 2014-09-24. Evidence and version limits below.
- **Earliest credible pre-cutoff related work:** [CERT CA-1996-22, 8 October 1996](https://www.sei.cmu.edu/library/file_redirect/1996_019_001_496172.pdf/), pp. 128–130: Bash interpreted byte 255 as a command separator, exposing CGI programs that passed user strings into commands. Its revised 1997 text remains safely before this cutoff.
- **Closest pre-cutoff equivalent work:** That advisory is a related parser-injection precedent, but requires a command-string sink. [RFC 3875, October 2004](https://www.rfc-editor.org/info/rfc3875/), §4.1.18, describes HTTP request metadata passed as CGI variables; this is a transport precondition, not an earlier Shellshock exploit. No equivalent arbitrary-name environment import/trailing-command disclosure was verified before September 2014.
- **Evidence boundary:** The archived CVE record was read in full but supplies later reference history. The scored evidence is the [24 September original oss-security disclosure](https://www.openwall.com/lists/oss-security/2014/09/24/10) and the original section of [Red Hat’s same-day technical explanation](https://www.redhat.com/en/blog/bash-specially-crafted-environment-variables-code-injection-attack). Explicit September 25–30 updates, later parser variants, and exploitation history are excluded.
- **Candidate's distinct contribution as of the cutoff:** Moves the dangerous interpretation point from explicitly assembled command text to automatically consumed environment data. The variable name need not itself select a special shell option, so prefixed CGI metadata is still a route.

## Scorecard

| Category | Score | Weight | Weighted score | Reason |
|---|---:|---:|---:|---|
| Original contribution | 78/100 | 25% | 19.50/25 | A non-obvious implicit execution route under different constraints from the earlier command-string parser injection. |
| Transferability | 80/100 | 20% | 16.00/20 | The primitive requires Bash, but the startup-import trust boundary crosses CGI, restricted command wrappers, and other process integrations described at disclosure. |
| Lasting value | 82/100 | 20% | 16.40/20 | Supports future audits of automatic interpretation at process boundaries, beyond enumerating vulnerable scripts. |
| Technical soundness | 88/100 | 15% | 13.20/15 | The original disclosure and vendor explanation connect parsing, startup, variable names, and realistic trigger conditions precisely. |
| Practical usability | 85/100 | 10% | 8.50/10 | A small local diagnostic and clear process prerequisites make the finding directly actionable for testing. |
| Clarity and reproducibility | 90/100 | 10% | 9.00/10 | The original example isolates the cause and the vendor explains reachable and non-equivalent integration cases. |

**Final score: 82.6/100** (exceptional)

## Reverification

- **Candidate facts rechecked against:** Reopened the September 24 disclosure and original Red Hat section; compared CERT’s original parser description and the CGI specification.
- **Cutoff audit:** Dates and original-version exclusions are recorded above. Publication-time evidence is used for all six categories; potential is the evaluator's forecast, not observed later influence.
- **Independent prior-art check:** After local environment/function/CGI searches, separately searched historical Bash CGI injection and followed the CERT advisory. It supplies an actual older attack rather than merely showing that function export existed.
- **Strongest challenge to the result:** Both works are Bash parser flaws reaching web-server execution. Treating that shared outcome as enough would erase the new implicit sink; conversely, Bash dependence prevents assuming the literal payload works across arbitrary interpreters.
- **Benefit-of-doubt check:** The disclosure exposes a previously unsuspected place where data becomes executable during startup, with several concrete integrations already evident at publication.
- **Changes after reverification:** Added the 1996 CGI/Bash injection comparison on the second pass. Kept the score because the sink and required application behaviour differ materially; the older component and vulnerability label do not establish duplication.

## Verdict

**Original technique**

- **Archive decision:** Include as a core technique
- **Confidence:** Medium
- **Reasoning:** An original execution route with a reusable process-boundary audit lesson. The lack of a located exact predecessor is a search limit, not proof of first discovery.
- **Evidence gaps:** Search does not exhaust all pre-2014 mailing lists or unpublished knowledge. Only the original Shellshock mechanism is scored, not subsequent bypasses.

# Research Evaluation

## Candidate

- **Title:** Poodle (2014 rank 3)
- **Author or organisation:** Bodo Möller, Thai Duong, Krzysztof Kotowicz (Google).
- **Publication date:** 2014-10-14 public disclosure; manuscript labelled September 2014
- **Reference:** [Nominated reference](https://web.archive.org/web/20160403035045/https://www.openssl.org/~bodo/ssl-poodle.pdf); [local archive](../../archived-references/md/2014/poodle.md).

## Core Contribution

Combine browser protocol fallback, attacker-influenced request layout, and SSL 3.0’s unauthenticated CBC padding to recover selected plaintext through an acceptance oracle. The added understanding is that retrying an older protocol can expose a simple oracle even when the preferred protocol handles padding differently.

## Prior Art

- **Novelty cutoff:** 2014-10-14 public disclosure; manuscript labelled September 2014. Evidence and version limits below.
- **Earliest credible pre-cutoff related work:** [OpenSSL advisory, 4 January 2012](https://openssl-library.org/news/secadv/20120104.txt), CVE-2011-4108, documents an earlier DTLS CBC padding/timing oracle. The local [Practical Padding Oracle Attacks, May 2010](../../archived-references/md/2010/practical-padding-oracle-attacks.md) predates this and develops padding-oracle exploitation in other settings.
- **Closest pre-cutoff equivalent work:** Earlier CBC oracle work is the relevant family. The candidate itself cites Vaudenay (2002), BEAST (2011), and Lucky Thirteen (2013); the local [Lucky Thirteen original-disclosure material](../../archived-references/md/2013/isg-rhul-ac-uk-lucky-thirteen-breaking-tls-dtls-record-protocols.md) confirms TLS/DTLS CBC analysis was established. None of those facts alone demonstrates the SSL 3.0 fallback plus full-padding-block replacement construction.
- **Evidence boundary:** Read the full four-page [original advisory](https://www.openssl.org/~bodo/ssl-poodle.pdf). Its September manuscript date is not treated as a proven public release: the [author’s publication announcement is 14 October 2014](https://security.googleblog.com/2014/10/this-poodle-bites-exploiting-ssl-30.html). Later TLS implementations called POODLE, browser retirement, and adoption of proposed mitigations are excluded.
- **Candidate's distinct contribution as of the cutoff:** The SSL 3.0 padding format enables a simpler block-replacement oracle, assembled with browser request alignment and fallback. It adds a concrete security consequence of compatibility retries beyond the already known padding-oracle concept.

## Scorecard

| Category | Score | Weight | Weighted score | Reason |
|---|---:|---:|---:|---|
| Original contribution | 75/100 | 25% | 18.75/25 | A substantial combination and protocol-specific construction; does not invent CBC padding oracles. |
| Transferability | 78/100 | 20% | 15.60/20 | The compatibility-retry and authentication-boundary lesson extends beyond one implementation; the literal oracle depends on SSL 3.0 CBC. |
| Lasting value | 85/100 | 20% | 17.00/20 | Grounded potential for testing fallback paths and whether selected protocol modes authenticate all relevant semantics. |
| Technical soundness | 92/100 | 15% | 13.80/15 | The short advisory explains padding conditions, block substitution, expected trial count, and relevant client behaviour. |
| Practical usability | 65/100 | 10% | 6.50/10 | Useful research construction, but an active intermediary, suitable browser requests, and fallback/CBC prerequisites constrain use. |
| Clarity and reproducibility | 86/100 | 10% | 8.60/10 | Compact but precise protocol and request-layout explanation; integrating the complete network/browser harness still requires work. |

**Final score: 80.2/100** (exceptional)

## Reverification

- **Candidate facts rechecked against:** Reread the original advisory, its author announcement, the local 2010 padding-oracle paper, and the 2012 vendor oracle disclosure.
- **Cutoff audit:** Dates and original-version exclusions are recorded above. Publication-time evidence is used for all six categories; potential is the evaluator's forecast, not observed later influence.
- **Independent prior-art check:** Repeated the search through older CBC and downgrade work rather than the POODLE name, including the candidate’s backward citations and local pre-2014 padding/fallback searches.
- **Strongest challenge to the result:** Padding oracles and browser-controlled repeated requests were already known. The score credits the particular SSL 3.0 construction and fallback combination rather than awarding a new vulnerability class.
- **Benefit-of-doubt check:** Its strongest reusable contribution is analysing security across compatibility modes; that remains a plausible research programme at publication even if this exact protocol path is removed.
- **Changes after reverification:** Used October public disclosure rather than the September manuscript label. Retained a combination verdict and excluded later TLS variants from evidence and potential.

## Verdict

**Meaningful combination or adaptation**

- **Archive decision:** Include as a core technique
- **Confidence:** Medium
- **Reasoning:** An established cryptanalytic family is turned into a distinct, well-explained attack through a concrete protocol composition. The future-value score is a forecast from that lesson.
- **Evidence gaps:** The older Möller TLS-CBC note could not be fetched directly; it remains a bibliography lead, not an independently verified equivalent. No exploit harness was run.

## Candidate

- **Title:** FREAK (Factoring Attack on RSA-Export Keys) (2015 rank 1)
- **Author or organisation:** Benjamin Beurdouche, Karthikeyan Bhargavan, Antoine Delignat-Lavaud and the SMACK TLS research collaborators; the nominated tracking site is by the Michigan measurement team.
- **Publication date:** 2015-01-08 client acceptance defect; 2015-03-03 complete public FREAK combination
- **Reference:** [Nominated reference](https://www.freakattack.com/); [local archive](../../archived-references/md/2015/freakattack-com-tracking-freak-attack.md).

## Core Contribution

A client accepts a weak temporary export-RSA key in a stronger negotiation. An intermediary can obtain a legitimate server’s reusable export key, factor it ahead of time, and then complete altered handshakes. The useful addition combines state-machine acceptance, legacy cryptography, and amortised attack preparation.

## Prior Art

- **Novelty cutoff:** 2015-01-08 client acceptance defect; 2015-03-03 complete public FREAK combination. Evidence and version limits below.
- **Earliest credible pre-cutoff related work:** [OpenSSL’s 8 January 2015 advisory](https://openssl-library.org/news/secadv/20150108.txt), CVE-2015-0204, already disclosed the project’s client-side export-key acceptance defect. This is an earlier component cutoff for the same research, not an unrelated predecessor deserving a duplicate penalty.
- **Closest pre-cutoff equivalent work:** [One Bad Apple: Backwards Compatibility Attacks on State-of-the-Art Cryptography, NDSS 2013](https://www.ndss-symposium.org/wp-content/uploads/2017/09/10_4_0.pdf) ("One Bad Apple") is verified earlier work on how legacy cryptographic modes can undermine stronger modes in XML and JSON cryptography. It does not supply the specific export-RSA acceptance plus cached-key factoring chain. The archive contains a full copy under the 2013 collection.
- **Evidence boundary:** Read the complete nominated tracking page, but exclude its changing March prevalence table. Use the January vendor disclosure and the [coordinated 3 March technical explanation](https://blog.cryptographyengineering.com/2015/03/03/attack-of-week-freak-or-factoring-nsa/). The later IEEE paper’s FREAK section corroborates that chain only; its broader state-machine research, subsequent fixes, and revised scan results are not imported.
- **Candidate's distinct contribution as of the cutoff:** January contributes the client negotiation flaw. March adds the full legitimate-server intermediary attack and makes factoring useful within handshake constraints by exploiting repeated use of the same weak temporary server key.

## Scorecard

|---|---:|---:|---:|---|

| Transferability | 80/100 | 20% | 16.00/20 | A reusable way to inspect combinations of negotiated modes, accepted messages, and cached cryptographic material. |
| Lasting value | 82/100 | 20% | 16.40/20 | Supports future protocol-state and compatibility analysis, with attack economics grounded in key reuse. |
| Technical soundness | 86/100 | 15% | 12.90/15 | The disclosed causal chain includes why legitimate signatures do not prevent the altered exchange and how precomputation fits the attack. |
| Practical usability | 65/100 | 10% | 6.50/10 | Requires an active intermediary, a susceptible client, an export-enabled server, and advance factoring effort. |
| Clarity and reproducibility | 78/100 | 10% | 7.80/10 | The original technical account explains the complete chain; the nomination’s tracking page is not itself a full implementation guide. |

**Final score: 77.6/100** (strong)

## Reverification

- **Candidate facts rechecked against:** Reopened the January advisory and March technical disclosure and compared the FREAK section of the full local IEEE paper.
- **Cutoff audit:** Dates and original-version exclusions are recorded above. Publication-time evidence is used for all six categories; potential is the evaluator's forecast, not observed later influence.
- **Independent prior-art check:** Searched local pre-2015 backward compatibility/export/state-machine work, then independently followed the later paper’s earlier vendor-advisory references and the 2013 cross-mode paper.
- **Strongest challenge to the result:** The key acceptance flaw was public in January and RSA factoring was established. Treating the whole March report as an original mathematical attack would inflate it, but treating its own earlier component as a duplicate would erase the completed combination.
- **Benefit-of-doubt check:** The report turns a client oddity into a feasible intermediary attack using a legitimate server’s behaviour and attack preparation outside the handshake.
- **Changes after reverification:** Split the component cutoffs after identifying the January disclosure. Excluded the May paper’s wider testing framework and changing tracking figures; retained credit for the original combination.

## Verdict

**Meaningful combination or adaptation**

- **Archive decision:** Include as a core technique
- **Confidence:** Medium
- **Reasoning:** Strong research value comes from connecting state-machine and deployment assumptions. It earns no points for later uptake, publicity, or removal of export cryptography.
- **Evidence gaps:** The original smacktls project site was unavailable. The precise first public day of every auxiliary artifact is unresolved; no later tooling is assumed available in March.

## Candidate

- **Title:** LogJam (2015 rank 2)
- **Author or organisation:** David Adrian and collaborators, Imperfect Forward Secrecy research team; nominated overview by Bruce Schneier.
- **Publication date:** 2015-05-19–20; original author announcement and coordinated 20 May publication
- **Reference:** [Nominated reference](https://www.schneier.com/blog/archives/2015/05/the_logjam_and_.html); [local archive](../../archived-references/md/2015/schneier-com-logjam-another-vulnerability-against-diffie-hellman-key-exchange.md).

## Core Contribution

Combine an export-DH downgrade with per-prime discrete-log precomputation: shared weak groups allow preparation to be reused across many independently generated session keys. The research also evaluates what that amortisation implies for stronger common parameters. The durable insight concerns authenticated negotiation and the aggregate economics of shared cryptographic parameters.

## Prior Art

- **Novelty cutoff:** 2015-05-19–20; original author announcement and coordinated 20 May publication. Evidence and version limits below.
- **Earliest credible pre-cutoff related work:** The [1998 Oakley key-determination standard, RFC 2412](https://www.rfc-editor.org/info/rfc2412/) is background for standardised groups; it is not a prior exploit claim. Logjam instead exploits how DHE parameters are authenticated and reuses computation per group, rather than factoring each RSA modulus.
- **Evidence boundary:** Read the complete nominated May 21 overview, excluding its May 23–24 additions. The author [project](https://weakdh.org/) and [paper](https://weakdh.org/imperfect-forward-secrecy.pdf) were consulted for the underlying research. The present PDF is a later conference version, so score only the core also evidenced in the [coordinated vendor explanation of 20 May](https://openssl-library.org/post/2015-05-20-logjam-freak-upcoming-changes/). - **Candidate's distinct contribution as of the cutoff:** A protocol-level route for accepting export-DH parameters, combined with measured preparation against shared groups and a broader parameter-reuse threat analysis. ## Candidate

- **Title:** Web Timing Attacks Made Practical (2015 rank 3)
- **Author or organisation:** Timothy D. Morgan and Jason W. Morgan.
- **Publication date:** 2015-08-03–06; whitepaper dated 3 August, Black Hat USA publication week
- **Reference:** [Nominated reference](https://www.youtube.com/watch?v=KirTCSAvt9M); [local archive](../../archived-references/md/2015/web-timing-attacks-made-practical.md).

## Core Contribution

Systematise web timing tests using paired, randomised measurements, packet-based timing, statistical estimators, and an explicit training/testing process for estimating sample requirements and error. Nanown packages the workflow. Its value lies in improving how researchers distinguish a timing signal from noise and judge whether a test is feasible.

The local pre-2015 archive also contains earlier timing and padding-oracle research.
- **Closest pre-cutoff equivalent work:** [Mayer and Sandin, Time Trial, Black Hat USA 2014](https://blackhat.com/docs/us-14/materials/us-14-Mayer-Time-Trial-Racing-Towards-Practical-Timing-Attacks-WP.pdf) provides an earlier practical timing methodology and tool. The candidate explicitly compares that userspace measurement tool and earlier box tests with its own measurement and estimator choices.
- **Evidence boundary:** Read the full [43-page 2015 whitepaper](https://www.blackhat.com/docs/us-15/materials/us-15-Morgan-Web-Timing-Attacks-Made-Practical-wp.pdf) preserved locally, and the relevant original predecessor papers. The exact public upload day within the conference interval is not proven. Later timing tools, real-world uptake, and modern network behaviour are excluded.
- **Candidate's distinct contribution as of the cutoff:** An integrated paired-measurement, robust-estimator, packet-selection and feasibility-assessment workflow with comparative experiments.
