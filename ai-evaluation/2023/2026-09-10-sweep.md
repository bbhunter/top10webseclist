## Survivor 1 evidence digest — Shared Storage timing budget bypass

**Candidate:** “Leaking more than log_2(\|URLs\|) bits of data with the selectURL gate,” GitHub author `anisenoff`, [issue 86](https://github.com/WICG/shared-storage/issues/86). Main supplied this as a citation from the 2025 Nisenoff et al. paper. Attribute the issue to its verified account; the 2025 paper's extra authors and contributions are not automatically authors or content of this disclosure.

**Cutoff and version boundary:** GitHub REST metadata independently fetched twice gives `2023-06-05T21:00:15Z`. Same-day developer reply at 21:19 confirms the timing problem and explains private-rendering requirements. The issue's current `updated_at` is February 21, 2024, reflecting later thread activity; a full body edit history was not obtained. The June reply corroborates the central mechanism, while all explicitly dated 2024 comments are excluded. A historical author repository contains an April 19, 2023 wrapper and March 28 links labelled delayed requests, but only iframe scaffolding, with the worklet hosted elsewhere. That establishes earlier experimentation, not a defensible earlier full technical disclosure. Earliest verified substantive source here is June 5; exact-first-public confidence is medium, year confidence high.

**Full source read:** Entire issue body and all API-returned comments read; both original waterfall screenshots opened visually. The two screenshots show the same third-party iframe under `anisenoff.github.io` and `andrew.cmu.edu`, 20 same-resource requests with frame indices, and a matching delayed/undelayed pattern over roughly 21 seconds. They corroborate the author's two-site example; they are not an independent controlled execution or measured population study.

**Contribution:** A worklet may read its origin's intentionally unpartitioned Shared Storage, while its embedding document is supposed to learn only a bounded selection result. The attacker intentionally delays return according to a stored bit. Although `selectURL()` resolves an opaque handle promptly, the selected resource cannot actually be fetched until the worklet chooses it. A cooperating server distinguishes request arrival gaps and reconstructs bits across top-level sites. Giving the gate exactly one candidate URL costs `log2(1)=0`, so the timing output escapes the selection-entropy account. The disclosure also proposes multiple delay lengths; no multi-symbol throughput demonstration is supplied. Its final iframe-cache sentence is a hypothesis, not a demonstrated second attack.

**Preconditions and limits:** Attacker controls an embedded origin, its worklet and an observing resource server; Shared Storage must be available in the tested environment. This exports the attacker's own stored identifier across top-level partitions, not arbitrary third-party origins' storage or the user's general browser contents. The tested browser is author-stated Chrome 114.0.5735.90. Long enough dwell time and a usable network timing signal are needed. The June disclosure does not establish today's deployment or a universal release population. No current patch/deprecation history changes any score.

## Survivor 2 evidence digest — DOMLeakify

**Candidate:** arkark, “DOMLeakify” section of [SECCON CTF 2023 Finals: Author Writeups](https://blog.arkark.dev/2023/12/28/seccon-finals). Score only this bounded section, not the article's other independent CTF techniques.

**Cutoff:** December 28, 2023. The article displays that date. Primary repository history records [solver commit 0ed2199](https://github.com/arkark/my-ctf-challenges/commit/0ed219959ce92c56b378c4cce9caa389f4e2b90f) at `2023-12-28T12:44:57Z`. December 24 distribution files and December 26 build directories predate it but do not establish earlier public disclosure of the intended solver. No claim that the contest date alone communicates this method. The current solver equals the copy fetched at the immutable December 28 commit.

**Full bounded source read:** Entire DOMLeakify section, example application/configuration, intended method, inline timing code, limitations visible in that code, and complete original `solver/public/main.js` read. Other article sections received selected reading only and remain separate held leads. The original solution's textual/code evidence is sufficient to follow its causal chain; no independent historical Firefox run performed.

**Contribution and result:** The vulnerable page accepts sanitized HTML with `style` elements and `loading` attributes forbidden but inline style attributes allowed. An injected element sets its background to `-moz-element(#guessed-id)`. Firefox reflects an existing element as an image; a nonexistent ID has no image. A large scale transform and drop-shadow make the existing-image case expensive. An attacker document times the navigation of additional victim-origin popups to distinguish the graphics/browser busy state. This yields an exact ID-existence oracle from style attributes without injecting stylesheet selectors, executable victim script, or custom SVG filter markup. The challenge exposes every secret prefix as its own ID, so repeated exact ID tests recover the displayed flag prefix character by character.

**Precise limitations:** `-moz-element` is Firefox-specific in the source. The full exfiltration relies on the unusually convenient prefix-ID layout; it does not establish arbitrary attribute-prefix matching or extraction of arbitrary text using inline CSS. Outside the challenge the reusable primitive is testing guessed whole IDs, useful only when their existence is sensitive/guessable. The solver opens multiple windows and samples twice with a threshold three times the negative baseline; popup permission/user interaction, noise and rendering cost constrain practical use. The challenge uses headless Firefox with wasm/baseline JIT disabled. A large blur can crash the browser, so the oracle has a stability tradeoff, not a universally reliable remote read. DOMPurify's documented configuration is the injection boundary; this is not a JavaScript sanitizer bypass.

It is strong technique-level prior art, not just an old API specification.
