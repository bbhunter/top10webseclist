### Draft evaluation: Multiple Browsers Cross Domain Charset Inheritance

**Candidate and cutoff.** Stefan Esser, Hardened-PHP Project, Advisory 03/2007.
The complete [original Full Disclosure post](https://seclists.org/fulldisclosure/2007/Feb/548)
has the header **23 February 2007, 21:38:33 +0100**, and explicitly distinguishes
11 October 2006 private vendor notification from 23 February 2007 public disclosure.
The [author's next-day reply](https://seclists.org/fulldisclosure/2007/Feb/552)
explains that the October announcement only teased a Firefox trick, without
technical detail. The novelty cutoff is therefore **23 February 2007**, not
October 2006. The same-day [Mozilla advisory](https://www.mozilla.org/en-US/security/advisories/mfsa2007-02/)
independently describes the complete mechanism. Recovered full source bytes and
readable text: `/tmp/esser-charset-2007.html`, `/tmp/esser-charset-2007.txt`,
`/tmp/esser-followup-2007.html`, `/tmp/esser-followup-2007.txt`.

**Core contribution.** An attacker controls the parent document's encoding and
uses an iframe to impose it on a different origin's page that lacks an explicit
HTTP or META charset. Previously harmless-looking UTF-7 text in that victim
page becomes executable markup in the victim origin. This adds an attacker-
controlled cross-origin interpretation route to existing charset-XSS attacks,
including browsers without automatic UTF-7 detection. It requires accepted or
reflected attacker text, absent explicit victim charset, framing, and a visit
to the attacker's parent. It does not overwrite a correctly supplied charset.
The original lists Firefox through 2.0.0.1, IE7 and Opera9; it excludes IE6 and
Opera8. It explicitly declines to ship an exploit file, but explains the short
construction. No modern-browser execution was attempted.

**Prior art and the increment.**

- [Yair Amit / Watchfire, XSS vulnerabilities in Google.com](https://seclists.org/vulnwatch/2005/q4/74), **21 December 2005**: full advisory recovered and read in `/tmp/yair-utf7-2005.html` and `.txt`. Google redirection/error pages reflect UTF-7 despite ordinary escaping; IE's Auto-Select recognizes it near the start of the body. Thus encoded filter bypass, missing charset, and site XSS are already known. It does not supply attacker-parent inheritance for a browser that does not auto-detect UTF-7.
- [WebKit bug 6118](https://www2.webkit.org/show_bug.cgi?id=6118), **17–23 December 2005**: complete developer discussion read. It documents parent-to-subframe charset inheritance and proposes changing it for rendering compatibility. This is strong evidence that the component behavior predates Esser, but it does not describe the cross-origin UTF-7 filter-bypass attack. Do not turn component age into an exploit-duplication verdict.
- The 2006 local Google Search Appliance and encoding-filter threads already cover UTF-7 and user-selected output encoding. Relevant bodies include `archived-references/md/2006/sla-ckers-org-sla-ckers-org-web-application-security-forum-full-appliance.md` and `sla-ckers-org-bypassing-filters-encoding.md`. The selected earlier sections do not establish the malicious parent inheritance route.

The distinct unit is a **meaningful combination/adaptation**: moving control of
the victim's text interpretation to an unrelated embedding origin under the
no-charset condition. It is not a new UTF-7 payload and not merely a new target.

### Draft evaluation: Windows DNS Server Cache Poisoning

**Candidate and cutoff.** Amit Klein's full [13-page paper](https://dl.packetstormsecurity.net/papers/attack/Windows_DNS_Cache_Poisoning.pdf),
including both appendices and the prediction script, was recovered and read.
The cover's “March–June 2007” dates describe preparation/research, not public
release: §5 explicitly states public disclosure on **13 November 2007**.
The [original author release](https://seclists.org/bugtraq/2007/Nov/175) is dated
**13 November 2007, 20:26:43 +0200** and confirms that publication order.
Local source: `/tmp/klein-windowsdns-2007.pdf`; text at
`/tmp/klein-windowsdns-2007.txt` has a PDF font-mapping defect that renders many
spaces as `S`, so web extraction was used for normal prose and local extraction
for the complete appendix code. The source PDF itself is intact; this is not a
fault in an existing archived reference.

**Core contribution.** The paper performs black-box packet analysis of Windows
DNS transaction IDs and derives a useful partial generator model. The ID has
three random high bits, an eight-bit global counter and three structured low
bits, with two top bits zero. At a particular counter transition, the low bits
become zero, leaving eight possible next IDs. An attacker uses a browser-triggered
lookup and CNAME chain to reach that transition before redirecting resolution
to the target name, then races the legitimate answer with the small candidate
set. The static source port is observed from the induced query. Cache absence,
allowed recursion, source-spoofed UDP reachability, limited interference by
other DNS traffic, and winning the response race remain preconditions.
The contribution is a concrete prediction algorithm and reusable black-box
analysis, not invention of cache poisoning or browser-triggered CNAME chains.
The attacker does not send spoofed UDP from browser JavaScript.

**Closest prior work, all before November.**

- [Arce/Kargieman, BIND Vulnerabilities and Solutions](https://marc.info/?l=best-of-security&m=96843707620680), **22 April 1997**: original signed advisory, attack section read. It already explains recursive query-ID observation, predicting a small next-ID interval and racing spoofed replies, including Windows NT. The new paper attacks a later pseudo-random implementation instead of the old sequential counter.
- [CERT VU#457875](https://www.kb.cert.org/vuls/id/457875/), **19 November 2002**, last revision 18 October 2004: multiple simultaneous queries create a birthday advantage. Unlike that method, the candidate deliberately predicts the next ID without requiring hundreds of simultaneous requests for one name. The CERT dates are all pre-cutoff.
- **Klein, BIND 9 DNS Cache Poisoning, 24 July 2007.** The [author index](https://www.securitygalore.com/site3/dns_cache_poisoning) identifies the release; the original paper's content was read in its [contemporaneous 24 July reproduction](https://www.opennet.ru/base/netsoft/1185295090_11783.txt.html), `/tmp/klein-bind9-prior-2007.html` and `.txt`, especially §§2.1–2.3. The primary paper itself is [author-linked here](https://citeseerx.ist.psu.edu/document?doi=0c1e863b6698808b724def8793d7cba023494808&repid=rep1&type=pdf), but its direct retrieval failed. The copied technical sections explicitly already contain browser image → attacker authoritative server → CNAME conditioning → target query → small spoofed-response set. Its predictor attacks two clock-controlled LFSRs, with ten candidates in the basic attack and full-state recovery in the advanced case. None of that delivery route is newly credited to November.
- [Klein, BIND 8 DNS Cache Poisoning](https://dl.packetstormsecurity.net/papers/attack/BIND_8_DNS_Cache_Poisoning.pdf), **27 August 2007** per author release index: relevant §§3.1–3.2 and §5 read. It already derives linear-congruence predictors, uses a handful of consecutive IDs, and supplies CNAME collection routes. The Windows bit-field/counter invariant is different, but the overarching PRNG-analysis methodology is established.

The Windows source also cites Zalewski's 2001 attractor analysis and an April
2007 Windows-forwarder attack. The former's original URL returned 403 in this
pass; exact comparative sample-count claims are therefore treated as the
candidate author's statements, not independently verified benchmarks. The
candidate's forwarder variant is described, but no separate novelty bonus was
given without full verification of that April predecessor.

**Scanit relationship.** The complete [Alla Bezroutchko / Scanit advisory](https://seclists.org/fulldisclosure/2007/Nov/346)
is dated **14 November 2007, 13:07:28 +0100** and gives a separate 24 October
2006 private-report timeline. It proposes an empirical eight-sequence estimator
from 50–100 observations and a larger spoof set, describes a browser-driven
collector, and links a web analyzer and scripts. It explicitly credits Klein's
more precise eight-packet predictor. Scanit merits independent-discovery and
testing-artifact attribution within this cluster, not a second presumed new
poisoning primitive. Its next-day evidence is not imported into the November13
Klein score. The old web analyzer/scripts were not executed or independently
recovered; do not claim their current functionality.
