### 1. Talking About My Generation: Targeted DOM-based XSS Exploit Generation using Dynamic Data Flow Analysis

- Authors: Souphiane Bensalim, David Klein, Thomas Barber, Martin Johns.
- [Author institution paper](https://www.ias.cs.tu-bs.de/publications/talking_about_my_generation.pdf), [ACM record](https://doi.org/10.1145/3447852.3458718). The seven-page paper was read in full. Working copies: `/tmp/websec-sweep-2021/generation.pdf` and `.txt`.
- Date: primary paper identifies EuroSec on **26 April 2021**; ACM publication record agrees. October 2020 is the crawl date, not evidence of public disclosure. Exact-title searches did not identify a pre-2021 public version. Confidence in year high, in absolute first-day cutoff medium.
- Underlying contribution: retain the source-to-sink string relationship while deciding which URL characters to replace, preserving application routing and structured parameter syntax. This extends context-aware payload generation and taint tracking; neither is new here.
- Mechanism/evidence: character-level taint metadata includes string transformations. Six indices map the tainted substring and replaceable span in the URL to the corresponding sink positions. Unlike simply appending a payload or moving a query pair to the fragment, replacement stays in its original URL component, can retain JSON structure, and can account for URI decoding. The study reports 7,199 successful flows, with **846 exclusive to the new method** out of the union of 7,588. The headline 1.8/1.9 factors compare against individual baselines, not their combined coverage.
- Limits: URL-to-HTML/JavaScript flows only; automated crawl lacks authenticated interactions and deeper persistent/second-level flows. Crucially, the validation browser disables automatic URL encoding to resemble legacy IE; these counts do not demonstrate equivalent exploitability in stock modern Firefox. Some replacements change application paths or meet server filtering. This sweep confirmed the described experiment, not the reported vulnerabilities independently.
- Closest primary prior art: [25 Million Flows Later, 2013](https://publications.cispa.saarland/3/1/domxss.pdf), archived in `archived-references/md/2013/acm-ccs-2013-25-million-flows-later-large-scale-detection-dom-based-xss.md`, §§5.1–5.2 already generates context-sensitive breakout and escape sequences from byte taint. [Riding out DOMsday, 2018](https://www.cs.cmu.edu/~anupamd/paper/ndss2018.pdf), archived in `archived-references/md/2018/riding-out-domsday-towards-detecting-preventing-dom-cross-site-scripting.md`, §III-C already pinpoints query values by matching sink taint, but relocates the test to the URL fragment. Thus the defensible delta is precise in-place URL/sink span selection and structured-input preservation, with measured additional coverage, not the first targeted XSS generator. FLAX (2010), Kudzu (2010), and DexterJS (2015) surfaced as earlier taint/fuzzing/symbolic exploit-generation families; do not claim those broad primitives as new.
- Skeptical alternate query: `"DOM XSS" "URL" "exploit generation" before:2021-04-26` returned older 25 Million Flows and DexterJS. `"DOM XSS" "targeted" "2019" exploit generation` did not establish an earlier identical URL-span method. Later comparison papers were retrieval leads only and did not influence historical scores.
- Draft verdict: **Tooling / methodology contribution** (also plausibly meaningful extension); medium confidence pending main review.

### 2. Towards a Lightweight, Hybrid Approach for Detecting DOM XSS Vulnerabilities with Machine Learning

- Authors: William Melicher, Clement Fung, Lujo Bauer, Limin Jia.
- [Author paper](https://clementfung.me/gallery/papers/www2021-domxss-ml.pdf), [alternate author copy](https://www.contrib.andrew.cmu.edu/~liminjia/research/papers/www2021-dom-xss-dnn.pdf), [ACM record](https://doi.org/10.1145/3442381.3450062). All twelve pages read, including limitations, performance model, and references. Working copies `/tmp/websec-sweep-2021/domxss-ml.pdf` and `.txt`.
- Discovery: reference 10 of Talking About My Generation. The public conference source establishes WWW **19–23 April 2021**; ACM says publication 3 June 2021. Use April conference as conservative novelty cutoff; do not silently use June to admit intervening prior art. Search did not identify a 2020 public paper. Linked dataset's current API reports a March 2026 version: `/tmp/websec-sweep-2021/domxss-ml-dataset-metadata.json`. That current metadata cannot establish first release; the 2021 paper itself says data/models available. Do not date the research from the modern dataset revision.
- Contribution: a function-level classifier predicts potentially unsafe JavaScript, allowing costly taint analysis to focus on a subset. It reuses established dynamic tracking and exploit confirmation. Bag-of-AST-token counts, feature hashing, embedding and a small DNN are tested against linear baselines; the useful claim is a DOM-XSS prefilter, not replacement of dynamic confirmation.
- Evidence: the study trains on a large labelled crawl, distinguishes possible from confirmed flows, splits by scripts and separately measures unseen functions. Passing 2.5% of distinct functions retains 94.5% of distinct confirmed cases. The often-repeated **3.43× saving is a modeled cached, GPU-assisted, per-function case**, not an implemented end-to-end browser speedup. Entire scripts may need tracking; source identification and integration remain future work. The source explicitly finds a standalone classifier unsuitable because precision/recall tradeoffs are poor.
- Limits: old Chromium 57 and its encoding behavior; noisy negative labels from unexecuted paths; function duplication across initial script partitions; cross-function interactions not captured; training-code poisoning/evasion outside threat model. Claims about efficient future runtime deployment are author projections, not independently verified deployed functionality.
- Primary prior comparison: DOMsday (2018, local path above) supplies taint/confirmation machinery and the new work does not claim those as novel. [NeuTaint](https://arxiv.org/abs/1907.03756), first public 8 July 2019, already uses learned program behavior and saliency to improve taint analysis; it learns source/sink information-flow influence rather than this JavaScript source-code prefilter. [VulDeePecker](https://arxiv.org/abs/1801.01681), first public 5 January 2018, already uses code-gadget vectors and deep learning for vulnerability detection. These primary abstracts and the candidate's detailed related-work comparison establish substantial inherited machinery; full prior papers were not reread in this sweep. The remaining delta is a DOM-XSS-labelled function classifier and measured cost/recall operating points, a modest methodology adaptation.
- Fresh skeptical searches: `"machine learning" "taint tracking" "2019" NeuTaint`, `"DOM XSS" "machine learning" before:2021-01-01`, and `"Lightweight" "DOM XSS" "2020" Melicher`. Returned NeuTaint and general ML detection antecedents, plus later papers excluded from historical scoring. Prior-primary depth is lower than for survivor 1; main reviewer should verify the narrowly stated distinction before finalizing.
- Draft verdict: **Tooling / methodology contribution**, medium confidence. Scope follows the judge skill's acceptance of web-security testing tools; no new attack class claimed.

### NeuTaint: what was already public

NeuTaint §III trains a model of a **particular target program's dynamic behavior**:
concrete input bytes are the neural inputs and observed sink-variable values are
the outputs. Light instrumentation collects these pairs over varied executions.
Gradients of predicted outputs with respect to inputs produce coarse or
sink-specific saliency maps. Those maps rank bytes by influence; they are not
source-code vulnerability scores. §IV uses branch-condition sinks for parser and
fuzzer experiments, and chosen vulnerable variables for known-CVE analysis.
Models are trained per target, with different input/output dimensions. Its
benchmarks measure data collection, training and saliency costs and use the
influence ranking in a common fuzzing backend. Coverage and model error are
explicit limits (§IV-G). This already establishes learned analysis as a means of
reducing conventional taint-analysis cost, including neural features and
sensitivity-based inference. None of those broad ideas is new in 2021.

**Correction to the candidate's §2.5.** Describing both predecessors as relying on
C's static nature is too broad for NeuTaint. The latter deliberately learns from
executions rather than static dependency reconstruction or instruction semantics.
It still requires an instrumentable source/sink boundary and adequate training
runs, but the full paper does not establish that its approach fundamentally cannot
apply to JavaScript. The 2021 work provides no direct NeuTaint-on-JavaScript
comparison proving that stronger exclusion. Retain the actual methodological
difference, not that asserted impossibility.

### VulDeePecker: what was already public

VulDeePecker §§II–III already learns vulnerability patterns from source without
manually specifying the final classification rules. Its units are API-centered
**code gadgets assembled from static data-dependency slices**, which can cross
user-function boundaries. Forward/backward slicing follows whether the API
receives external input. User variable/function names are normalized, tokens are
embedded through word2vec, sequences are padded/truncated near the key API call,
and a BLSTM returns a vulnerable/non-vulnerable classification. Its original
implementation uses Checkmarx dependency information and evaluates C/C++ buffer
and resource-management errors. It neither proves taint flow dynamically nor uses
its predictions to selectively enable a browser's taint engine. Its data/label
construction, classifier comparisons, representation tradeoffs and published
corpus are substantial prior for the general 2021 learning workflow. Merely
replacing the language or neural architecture would be weak novelty evidence.

### The precise remaining 2021 delta

| Dimension | NeuTaint 2019 | VulDeePecker 2018 | DOM-XSS hybrid study 2021 |
|---|---|---|---|
| Learned input | Concrete input bytes for a target program | Ordered normalized tokens from API-centered dependency slices | Unordered AST-token frequency counts for JavaScript source functions, retaining names/constants |
| Learned output | Predicted runtime sink values | Vulnerable/non-vulnerable code gadget | Potentially unsafe function label learned from dynamic taint observations; separate confirmed-label experiments |
| Analysis role | Approximate source-to-sink influence with gradients | Direct static vulnerability classification/localization | Prefilter candidate functions/scripts before conventional dynamic taint analysis and exploit confirmation |
| Dependencies retained | Dynamic behavior over sampled executions | Explicit interprocedural data dependencies | No reconstructed interprocedural dependencies; loses ordering and context in the function bag |
| Evidence of utility | Influence/flow experiments and integrated fuzzing use | Classification and real-product matching of known vulnerabilities | Measured classifier cost/recall frontier; proposed integration and modeled browser overhead |

The addition is an **evaluated, inexpensive source-code selection stage for
DOM-XSS dynamic testing**, including what inexpensive local features can retain
and what they miss in a heavily imbalanced web crawl. Function segmentation,
feature hashing and a small feed-forward DNN avoid the candidate's attempted
static slicing/graph representations; these are choices of established
components, not new learning algorithms. Training a potential-flow classifier and
measuring its predictions against independently exploit-confirmed positives
supports the triage use case. The negative standalone result is useful too:
95% confirmed-case recall yields only 0.4% precision in the reported experiment.
That empirical result and the operating-point analysis add more than a new-target
example, but do not warrant a new attack-class or new taint-analysis claim.

The method also leaves the hardest integration boundary unresolved. The model
predicts a **sink-containing function**, not where tainted input first enters the
program. §6.1.1 explicitly leaves source identification/integration to future work.
Whole-script tracking may be needed. The 2.5% selected distinct-functions / 94.5%
distinct confirmed-recall point is a measured selection result. The 3.43× number
is an overhead-model scenario for a single function with caching and GPU
inference, not a measured complete hybrid browser. Its cost equation further
assumes a script is tracked if any constituent function is predicted positive.
Neither NeuTaint's measured speedups nor VulDeePecker's successful gadget
classification fills this 2021 implementation gap.
