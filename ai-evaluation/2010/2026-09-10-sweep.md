### Craig Heffner — How to Hack Millions of Routers / Remote Attacks Against SOHO Routers

**Source and public date.** Read all 36 pages' extracted text, including the attack
sequence captions, implementation, success/failure matrix, mitigations and
references, in the [official whitepaper](https://media.blackhat.com/bh-us-10/whitepapers/Heffner/BlackHat-USA-2010-Heffner-How-to-Hack-Millions-of-Routers-wp.pdf).
Local originals: `/tmp/missed-2010/routers.pdf` and `routers.txt`. Its title page
says **8 February 2010**, but that is a document date, not established public
availability. The [official Black Hat schedule](https://blackhat.com/html/bh-us-10/bh-us-10-schedule.html)
places the named presentation on **29 July 2010, 10:00–11:00**; the
[briefing abstract](https://blackhat.com/html/bh-us-10/bh-us-10-briefings.html)
announces the accompanying tool and live demonstration. Use 29 July as the
verified public technical presentation date, with a qualification that an earlier
paper upload has not been dated. July announcement search results describe an
upcoming disclosure; they do not establish February publication. The year is
securely 2010.

**Evidence digest.** The added capability is reaching a router's administrative
HTTP service without knowing its private address: rebind to the public WAN
address observed from the visiting client. Multiple-A DNS fallback first loads
attacker JavaScript, then a TCP refusal makes the browser use the router address.
With weak-end-system packet acceptance, a LAN packet addressed to a different
local interface's address is still accepted. When the HTTP service binds all
addresses and firewall restrictions select the incoming WAN interface, this LAN
request reaches administration despite remote administration being disabled.
The paper explains the routing and filtering conditions with configurations,
captures and a vendor matrix containing both successes and failures. Rebind adds
a browser-backed interactive HTTP proxy. Authentication still has to be satisfied
or separately exploited; this is an access primitive, not an automatic password
bypass. Private-address prioritization was a practical obstacle to the earlier
fallback attack that this public-address composition avoids.

**Closest public prior and distinctness.** Read the relevant mechanism and defense
sections of Jackson, Barth, Bortz, Shao and Boneh's
[2007 Protecting Browsers from DNS Rebinding Attacks](https://crypto.stanford.edu/dns/dns-rebinding.pdf),
including sections 3.1, 4.1 and the RFC1918-pinning discussion. Full PDF and text
are `/tmp/missed-2010/stanford2007.pdf` and `stanford2007.txt`. It already explains
multiple A records, deliberate connection refusal, subsequent XHR reads, browser
proxies and router reconfiguration. It also explicitly warns that public-address
space can be behind a firewall. Thus neither generic rebinding, public-address
protected resources, router compromise, nor the proxy deserves invention credit.
Heffner credits David Byrne's 2007 proxy presentation himself. What the inspected
prior does not describe is the specific router-WAN-address/weak-end-system/
interface-filter combination and its avoidance of private-address discovery and
ordering. The weak/strong end-system distinction itself is old networking
background, cited by Heffner; component age does not establish this exploit chain
was previously disclosed. This is also distinct from 2010's listed Java-applet
rebinding and NAT Pinning: it uses browser HTTP address fallback and local packet
acceptance, not Java DNS state or an application-protocol-induced port mapping.

**Independent skeptical pass.** Fresh searches for `"DNS rebinding" "weak end"
before:2010-07-29`, `"DNS rebinding" "weak end system" "2009"`, `"DNS rebinding"
"WAN" "2007"` and `"Protecting Browsers" "weak" rebinding` mainly returned the
candidate, later summaries, and the Stanford paper. Direct comparison with that
paper narrowed the novelty claim as above. No earlier matching composition was
verified; this bounded negative search is not proof of priority. A source-address
assumption and the stated service/filter configuration constrain deployment
coverage. Full text was inspected; diagram graphics were not separately rendered.

### oxod — Hitting Bitrix with a Hammer: FormCalc authenticated response reading

**Source and date.** Read both full Russian articles:
[1 September 2010](https://xakep.ru/2010/09/01/54715/) and the
[21 September same-title copy](https://xakep.ru/2010/09/21/53356/).
Both live pages display those dates; the September 21 page also links the earlier
article with its September 1 date. Earliest verified public date is **1 September
2010**. Current site byline is the magazine; the first-person author identifies
`oxod.ru` as their own blog. Use **oxod** provisionally, rather than inventing a
personal-name attribution. Recovered HTML/text: `/tmp/missed-2010/bitrix-sep1.html`,
`bitrix-sep1.txt`, `bitrix-sep1-body.txt`, and corresponding `bitrix-sep21.*` files.
Both bodies include the actual FormCalc code; the earlier extraction's missing
code is not a source-content absence or a repository archive fault.

**Evidence digest.** A user attaches a PDF to a Bitrix 9.0.3 support ticket. When an
administrator opens it inline through Adobe's browser plug-in on the application's
origin, FormCalc `Get` reads an authenticated admin response. `Substr`/`At` extract
the `sessid` anti-CSRF value; `Post` sends it with an administrative command. This
crosses the application's untrusted-upload boundary while satisfying the PDF
network model's same-origin permission check. The author reports a local test
producing an admin-side web shell with no PDF network prompt. The article provides
the three-line request chain and an iText Java routine to replace the XFA script
in a sample PDF. The separate BBCode/ICQ XSS and event-handler WAF bypass cases do
not constitute this contribution. The generalizable result is authenticated
response reading from uploaded active PDF content, defeating synchronizer-token
protection; the final Bitrix PHP execution feature is an impact demonstration.

**Closest public prior.** Fully read David Kierznowski's
[Backdooring PDF Files, 13 September 2006](https://web.archive.org/web/20070102032610/http://michaeldaw.org/md-hacks/backdooring-pdf-files/)
in `archived-references/md/2006/michaeldaw-org-backdooring-pdf-files.md`. It already
shows page-open script, warning-free URL launching in Reader 6/7, and an ADBC
enumeration/SOAP-exfiltration example. It does not show the uploaded same-origin
FormCalc authenticated HTML read → token extraction → administrative POST chain.
A fresh [March 2009 AcrobatUsers discussion](https://acrobatusers.com/forum/forms-livecycle-designer/javascript-equivalent-get-formcalc/)
explicitly demonstrates FormCalc GET returning HTML and substring/XML processing;
an [April 2010 discussion](https://acrobatusers.com/forum/general-acrobat-topics/javascript-blacklist-framework/)
reports XFA FormCalc HTTP POST functionality and compatibility trouble. These
strengthen the prior for the API components. Neither communicates the hostile
upload/authenticated token-read attack. The API's documentation and short code do
not by themselves make that security composition a rediscovery. Older universal
PDF XSS is another reason not to claim PDFs first became active-origin hazards in
2010; the candidate's route uses intended FormCalc networking rather than an
injected browser JavaScript fragment.

**Listed-item collision check and skeptical pass.** Read the archived
[Will It Blend? announcement](http://xs-sniper.com/blog/2010/12/17/will-it-blend/)
(`archived-references/md/2010/xs-sniper-com-billy-bk-rios-will-it-blend.md`). Its
December post describes a five-bug multi-plugin chain and changed Reader caching.
It is later than September and cannot be earlier novelty evidence. Its linked
PPTX could not be retrieved (network unreachable), so the earlier discovery
ledger's specific description of its internal mechanism is not independently
established by this follow-up. The announcement provides no evidence that it is
the same FormCalc upload contribution; final reviewer may retain that narrow
artifact-access limitation. Fresh queries included `"FormCalc" "CSRF"
before:2010-09-01`, `"FormCalc" "Get" "2009" security`, `"FormCalc" "security"
before:2010-09-01`, `FormCalc CSRF PDF 2008 2009`, `"PDF" "same origin" "2008"
CSRF`, `"PDF" "CSRF" "2006" FormCalc`, `"FormCalc" "cross site" attack` and
`"FormCalc" "token" "2010"`. Most results were API discussions, unrelated
formula-calculation software, or later exploitation writeups. Later FormCalc
research was not used to reward or penalize the 2010 contribution.

**Limits.** Requires attacker-controlled PDF served on the authenticated origin,
a supporting Adobe browser plug-in, and the administrator opening it. This is not
an unrestricted cross-origin read or a modern all-browser claim. The exact Reader
build is not specified. The published POST content-type spelling and some
